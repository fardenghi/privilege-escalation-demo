Escalamiento de Privilegios

De usuarios sin privilegios a SYSTEM/root. 2 sistemas operativos, 4 casos prácticos.

01 · Concepto

¿Qué es escalar privilegios?

Es pasar de un acceso limitado a otro de mayor poder dentro del mismo sistema, aprovechando una configuración, permiso o vulnerabilidad. En Linux la meta suele ser root; en Windows, Administrator o SYSTEM.

↑Vertical

Un usuario común pasa a administrador / root. Es lo que cubrimos hoy.

→Horizontal

Se accede a otra cuenta del mismo nivel para usar sus datos o permisos.

Secuencia habitual: acceso inicial → reconocimiento → escalamiento → objetivo final

02 · Conceptos base

Identidades, permisos y mínimo privilegio

Archivos, carpetas y servicios deciden quién puede leer, escribir o ejecutar. 1° regla defensiva → mínimo privilegio

LNXLinux

  • root (UID 0): superusuario.
  • rwx: permisos para dueño, grupo y otros.
  • SUID/SGID: ejecución con identidad del dueño o grupo.
  • sudo: comandos permitidos por reglas.
  • cron, PATH y capabilities: otros puntos a revisar.

WINWindows

  • Administrator y SYSTEM: identidades privilegiadas.
  • SID y token: identidad y privilegios de cada proceso.
  • Servicios: pueden correr como SYSTEM.
  • UAC: confirmación de elevación.
  • MSI: instalador afectado por AlwaysInstallElevated.
03 · Método

De la enumeración a la comprobación

01Enumerar

Identidad, grupos, permisos, binarios, servicios, tareas, archivos escribibles y versiones.
Es la búsqueda del descuido.

02Identificar

Elegir un vector concreto y comprobar sus requisitos: por ejemplo, un SUID abusable o una ruta de servicio escribible.

03Explotar

Ejecutar una acción con los permisos elevados que aporta ese vector

04Comprobar

Verificar la identidad del proceso elevado: id y UID efectivo 0 en Linux; whoami dentro del proceso en Windows.

Las herramientas automáticas ayudan a enumerar, y algunas a identificar.

Sistema · Windows

Windows

El objetivo es obtener privilegios de Administrator o NT AUTHORITY\SYSTEM. Dos configuraciones peligrosas:

  • Caso W1 — Unquoted Service Path
  • Caso W2 — Política AlwaysInstallElevated

Enumeración: winPEAS.exe / PowerUp.ps1 → buscan rutas sin comillas, servicios modificables y la política de instaladores MSI.

Caso W1 · Unquoted Service Path

Ruta de servicio sin comillas

01La debilidad

Un servicio se registra con una ruta con espacios y sin comillas. Windows no sabe dónde termina el ejecutable, así que prueba candidatos de izquierda a derecha:

C:\Program Files\Vuln Service\bin\srv.exe→C:\Program Files\Vuln Service\bin\srv.exe
1) C:\Program.exe
2) C:\Program Files\Vuln.exe
3) C:\Program Files\Vuln Service\bin\srv.exe ← intención real

02La explotación

Si el usuario tiene permiso de escritura en la ubicación de un candidato, coloca allí un binario de prueba. Cuando el servicio se inicia de nuevo y corre como SYSTEM, Windows puede ejecutar ese binario.

cmd · laboratorio
C:> wmic service get name,pathname,startmode C:> icacls "C:\Program Files" BUILTIN\Users:(OI)(CI)(W) # escribible ✱ C:> copy payload.exe "C:\Program Files\Vuln.exe" C:> sc stop VulnSvc C:> sc start VulnSvc [+] Verificar la acción del binario ejecutado como SYSTEM

🛡Remediación / Hardening

  • Encomillar siempre el ImagePath: "C:\...\srv.exe".
  • Quitar permisos de escritura de usuarios sobre C:\ y carpetas de programa.
  • Auditar con PowerUp/winPEAS y corregir en el hardening base.

Caso W2 · AlwaysInstallElevated

Instaladores MSI con privilegios elevados

01La debilidad

La política AlwaysInstallElevated permite instalar paquetes MSI con privilegios elevados. Para que exista el vector, el valor REG_DWORD 0x1 debe estar presente en HKCU y HKLM; una sola rama no alcanza.

cmd · enumeración
C:> reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated C:> reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated Ambas respuestas: REG_DWORD 0x1

02Explotación y comprobación

Un usuario común ejecuta un MSI preparado para realizar una acción privilegiada. La política eleva la instalación; la consola que lanzó msiexec no cambia de identidad y ejecuta el código malicioso con privilegios de SYSTEM

cmd
C:> msiexec /quiet /qn /i C:\ruta\prueba.msi [+] Verificar la acción privilegiada del MSI en el equipo de prueba

🛡Remediación / Hardening

  • Desactivar AlwaysInstallElevated en HKCU y HKLM (valor 0 o ausente).
  • Distribuir software mediante herramientas corporativas controladas.
  • Auditar ambas ramas del registro, no sólo una.

Sistema · Linux

Linux

El objetivo es pasar de un usuario común a root (uid=0). Dos técnicas clásicas:

  • Caso L1 — Binario SUID abusable (GTFOBins).
  • Caso L2 — Mala configuración de sudo (NOPASSWD).

Enumeración: linPEAS.sh / find / -perm -4000 / sudo -l → buscan SUID, capabilities, cron y reglas de sudo.

Caso L1 · Binario SUID

SUID root abusable (GTFOBins)

01La debilidad

Un binario con el bit SUID se ejecuta con permisos del dueño. Si el dueño es root y el binario permite ejecutar comandos, obtenemos un shell root.

-rwsr-xr-x   root root   /usr/bin/find

La s en el bloque del dueño = SUID activo

02La explotación

Buscamos SUID inusuales y consultamos GTFOBins para el "escape" del binario:

bash
$ find / -perm -4000 -type f 2>/dev/null /usr/bin/find $ find . -exec /bin/sh -p \; -quit # id → euid=0(root)

La opción -p conserva el UID efectivo elevado

Caso L2 · sudo mal configurado

Reglas de sudo permisivas

01La debilidad

Una regla en /etc/sudoers permite ejecutar un programa como root. El riesgo está en autorizar uno que abre una shell o ejecuta comandos; NOPASSWD permite hacerlo sin contraseña.

user ALL=(ALL) /usr/bin/echo
user ALL=(ALL) NOPASSWD: /usr/bin/vim  ← peligroso

02La explotación

Listamos permisos con sudo -l y usamos el escape del binario permitido (GTFOBins):

bash
$ sudo -l (ALL) NOPASSWD: /usr/bin/vim $ sudo vim -c ':!/bin/sh' # whoami → root

Sin un programa con escape, no hay salto directo. Si la regla exige contraseña y no la conocemos, sudo detiene el intento.

🛡Remediación / Hardening

  • Principio de mínimo privilegio en sudoers; evitar NOPASSWD.
  • Nunca permitir binarios con escape (vim, find, less, awk) vía sudo.
  • Para editar archivos, usar sudoedit. Validar reglas con visudo y auditarlas periódicamente.

04 · Enumeración automática

Qué busca cada herramienta

LNXLinPEAS

SUID/SGID, reglas de sudo, cron, PATH, permisos de escritura, capabilities, versiones y posibles credenciales expuestas.

WINWinPEAS

Servicios y rutas débiles, AlwaysInstallElevated, privilegios del token, tareas modificables y credenciales guardadas.

PSPowerUp

Invoke-AllChecks revisa servicios modificables, rutas sin comillas, AlwaysInstallElevated y secuestro de DLL. Puede sugerir comandos para validar hallazgos.

Cierre · Remediación

Defender cada vector

  • SUID: quitar el bit cuando no es necesario; inventariar binarios y preferir capabilities puntuales.
  • sudo: permitir sólo comandos acotados, evitar editores con escape y usar sudoedit.
  • Servicio Windows: encomillar la ruta y restringir escritura en las carpetas candidatas.
  • AlwaysInstallElevated: desactivar la política en HKCU y HKLM; distribuir software de forma controlada.

En todos los casos: mínimo privilegio, actualizaciones y auditoría periódica.
